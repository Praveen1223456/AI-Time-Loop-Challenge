# AI Time-Loop Challenge --- Product & Technical Specification

**File:** `spec.md`\
**Version:** 1.0\
**Status:** MVP specification for spec-driven development with Codex\

------------------------------------------------------------------------

## 1. Product Summary

AI Time-Loop Challenge is an interactive, AI-assisted narrative game.
The player is trapped in a repeating period of time and must uncover
what causes a key event---such as a station disaster, a museum theft, a
spaceship malfunction, or a mysterious disappearance---before the loop
resets.

The world resets after each loop, but the player retains knowledge and
selected discoveries. The player uses that knowledge to change actions,
reveal new information, and eventually reach a stable solution.

**Core promise:** Every loop teaches the player something useful, and
the final outcome is determined by explicit game state and rules---not
by an unconstrained AI decision.

### MVP example

Scenario: "A research station will lose power at 9:00 PM. The player has
15 minutes to discover why and prevent it."

-   Loop 1: The player explores the station and discovers an unusual
    alarm.
-   Loop 2: The player uses knowledge from Loop 1 to question an
    engineer.
-   Loop 3: The player accesses a restricted maintenance log.
-   Final loop: The player performs the correct sequence of actions to
    prevent the outage.

The scenario, characters, events, clues, and possible endings are
generated by Gemini and validated by the backend.

## 2. Goals and Non-Goals

### Goals

-   Generate a playable fictional time-loop scenario from a user prompt.
-   Provide a clear loop objective, countdown, locations, characters,
    and actions.
-   Reset temporary world state at the end of each loop.
-   Preserve knowledge, discovered clues, and selected progression
    across loops.
-   Make actions produce consistent, understandable consequences.
-   Track the causal chain behind the central event.
-   Provide multiple endings where practical.
-   Explain the final outcome using facts already introduced in the
    game.
-   Work on desktop and mobile browsers.

### Non-goals for the MVP

-   Multiplayer or shared worlds.
-   Real-time 3D gameplay.
-   Open-ended simulation of every possible action.
-   Voice generation or animated video generation.
-   Autonomous AI agents that execute external actions.
-   User-created public story marketplace.
-   Payments, subscriptions, or social leaderboards.

## 3. Target Users

1.  **Interactive story players:** enjoy branching narratives and

2.  **Casual gamers:** want short sessions with clear objectives.
3.  **Mystery and strategy fans:** enjoy connecting clues and planning

4.  **Portfolio reviewers:** should be able to see full-stack

## 4. Core Gameplay Loop

1.  The player enters a scenario or chooses a sample scenario.
2.  The backend generates and validates a scenario blueprint.
3.  The player starts a loop with a fixed number of turns or an in-game
    timer.
4.  The player visits locations, inspects objects, talks to characters,
    and performs actions.
5.  Events unfold according to a deterministic rules engine.
6.  The loop ends when time runs out or the player triggers the reset.
7.  Temporary world state resets.
8.  Persistent knowledge, discovered clues, and permitted unlocks
    remain.
9.  The player uses accumulated knowledge to access new actions and
    alter outcomes.
10. The game ends when the player meets the scenario's victory
    conditions or exhausts the configured loop limit.
11. The results screen explains the causal chain and the ending reached.

### Key distinction

The AI authors the story content and can suggest dialogue or narrative
descriptions. The backend owns the rules, state transitions, loop reset,
action validation, inventory, clue discovery, and win/loss conditions.

## 5. Functional Requirements

### FR-01: Landing Page

Provide: - Product title and concise explanation. - "Start a Time Loop"
primary action. - Sample scenario cards. - Short "How to Play"
section. - Responsive navigation and footer.

### FR-02: Scenario Creation

Allow the player to: - Enter a scenario prompt. - Select a theme:
Sci-Fi, Mystery, Fantasy, Disaster, Historical Fiction, or Custom. -
Select difficulty: Easy, Medium, Hard. - Select loop length: Short,
Standard, Long. - Start generation.

Validation: - Scenario prompt must be 30--1,000 characters. - Prevent
duplicate submissions while generating. - Show progress and recoverable
errors. - Treat user input as untrusted story content, not as
instructions that override application rules.

### FR-03: Scenario Generation

Generate a structured blueprint containing: - Scenario title and
premise. - Central event to prevent, explain, or resolve. - Loop
duration and turn budget. - Three to five locations. - Three to six
characters. - Six to twelve discoverable clues. - A causal chain
explaining the central event. - Available actions and prerequisites. -
Reset rules. - Persistent knowledge rules. - Victory and failure
conditions. - Two or more possible endings where feasible. - A private
solution guide for validation and the results screen.

The backend must validate the blueprint before the game becomes
playable.

### FR-04: Game World

Display: - Current loop number. - Current in-game time or remaining
turns. - Scenario objective. - Current location. - Available actions. -
Character interactions. - Discovered clues. - Inventory or carried items
when relevant. - Persistent knowledge journal. - Reset or restart action
when allowed.

### FR-05: Player Actions

Support a controlled list of actions: - `inspect`: examine an object or
location. - `talk`: speak to a character. - `travel`: move to another
location. - `use_item`: use an acquired item. - `interact`: operate a
device or trigger a defined event. - `wait`: advance time. -
`reset_loop`: end the current loop early, if permitted.

Each action must be checked against the scenario blueprint and current
state. Unknown or invalid actions must not mutate the game.

### FR-06: Dialogue

Characters may reveal information based on: - Current loop. - Time of
day. - Previously discovered clues. - Player inventory. - Prior actions
in the current loop. - Persistent knowledge or unlocks.

The same action under the same game state should lead to a consistent
outcome. AI may phrase dialogue naturally, but must not silently change
facts or invent new game mechanics.

### FR-07: Time and Events

-   Each action has a configured time cost.
-   Important events occur at defined times or state thresholds.
-   The game must show relevant upcoming or recently triggered events.
-   Time progression must be handled by backend rules.
-   The player must receive a clear indication when time expires.
-   The timer should be turn-based for the MVP; a real-time countdown
    can be added later.

### FR-08: Loop Reset

When a loop ends: - Reset temporary character positions and schedules. -
Reset temporary inventory unless an item is explicitly persistent. -
Reset temporary object states. - Reset loop-specific dialogue flags. -
Restore the initial time and temporary world state. - Preserve
discovered knowledge, persistent clues, unlocked actions, and progress
flags according to the blueprint. - Increment the loop number. - Show a
concise recap of what was learned.

Reset must be an explicit server-side state transition and must be
tested for consistency.

### FR-09: Persistent Knowledge Journal

Show information retained across loops: - Discovered clues. - Character
facts. - Important timestamps. - Unlocked locations or actions. -
Player-written notes. - Confirmed causal relationships.

The journal must distinguish confirmed facts from the player's own
hypotheses.

### FR-10: Hint System

Offer three hint levels: 1. Gentle direction toward a location or
person. 2. A clue or relationship to reconsider. 3. A stronger hint
toward the next useful action.

Hints must be grounded in the validated blueprint and discovered facts.
Hints must not create new clues or change the solution.

Optional: track hint usage in the final score.

### FR-11: Victory and Failure

Victory occurs only when a server-validated set of conditions is met.
Examples: - Prevent the central event. - Identify the correct cause and
complete the required actions. - Reach a specified ending with required
persistent knowledge.

Failure may occur when: - The loop limit is reached. - The player
selects an explicitly defined failure outcome. - A critical resource is
exhausted, if the scenario uses resources.

Do not declare victory solely because Gemini says the player has
succeeded.

### FR-12: Endings and Recap

Display: - Ending title and narrative. - Whether the main objective was
completed. - Final loop count. - Key clues discovered. - Important
decisions. - Explanation of the causal chain. - Missed clues or optional
objectives. - Restart or replay option.

All explanations must be grounded in the scenario blueprint and recorded
game events.

### FR-13: Save and Resume

For the MVP: - Persist the game state in MongoDB. - Allow the player to
resume an active game through a session-bound game ID. - Store a basic
game history for the active session.

If authentication is added later, enforce ownership on every game and
history endpoint.

    |

    |
    +-- Ending Evaluator
    |

### Architecture rules

-   The frontend never calls Gemini directly.
-   The backend is authoritative for game state.
-   AI output is treated as untrusted input until validated.
-   Game state transitions must be deterministic.
-   AI must not decide whether an action is legal.
-   AI must not directly write arbitrary database updates.
-   Store the blueprint and live state separately where practical.
-   Do not return internal solution fields to the client during active
    play.
-   All endpoints must validate input and handle errors consistently.

### Data integrity rules

-   Every ID reference must resolve.
-   Every action effect must use an allowlisted effect type.
-   The loop counter must only increase through the reset service.
-   Persistent state may only contain fields explicitly allowed by the
    blueprint.
-   The client cannot submit an entire replacement game state.
-   Validate state transitions on the server before saving.
-   Use atomic updates or transactions where needed to prevent
    conflicting writes.

## 11. API Contract

Base path: `/api/v1`

### Create scenario

`POST /scenarios`

Request:

``` json
{
  "prompt": "A research station loses power at 9 PM, and I must prevent it.",
  "theme": "sci-fi",
  "difficulty": "medium",
  "loopLength": "standard"
}
```

Response:

``` json
{
  "success": true,
  "data": {
    "scenarioId": "SCENARIO_ID",
    "title": "Nine Minutes to Darkness"
  }
}
```

Do not return the private solution guide.

### Start a game

`POST /games`

``` json
{
  "scenarioId": "SCENARIO_ID"
}
```

Returns a new game ID and initial public state.

### Get current game state

`GET /games/:gameId`

Returns the current public state, visible locations, available actions,
journal, and inventory. Do not include hidden solution fields.

### Perform an action

`POST /games/:gameId/actions`

``` json
{
  "actionId": "inspect_control_panel",
  "targetId": "control_panel"
}
```

The server validates the action, checks prerequisites, applies
deterministic effects, advances time, records events, and returns the
updated public state.

### Reset loop

`POST /games/:gameId/reset`

``` json
{
  "reason": "manual"
}
```

The server applies reset rules and returns the next loop's public state
and recap.

### Request a hint

`POST /games/:gameId/hints`

``` json
{
  "level": 1
}
```

Returns a hint grounded in the scenario and current progress.

### Get ending

`GET /games/:gameId/ending`

Only succeeds when the game is completed. Returns the ending and
permitted explanation.

### List history

`GET /games`

Returns games accessible to the current session, with pagination where
appropriate.

### Error format

``` json
{
  "success": false,
  "error": {
    "code": "INVALID_ACTION",
    "message": "That action is not available in the current state."
  }
}
```

Use appropriate status codes: 200, 201, 400, 403, 404, 409, 429, 502,
and 500.

## 12. Game Engine Rules

### Deterministic state transitions

Every action should follow this sequence:

1.  Load the game session and validated scenario blueprint.
2.  Confirm the session is active and accessible.
3.  Validate the action ID, target, location, prerequisites, and time
    cost.
4.  Apply allowed effects using server-side rules.
5.  Advance in-game time.
6.  Trigger scheduled events in a stable order.
7.  Record the action and resulting events in the event log.
8.  Evaluate failure and victory conditions.
9.  Persist the updated state.
10. Return the public state.

### Reset algorithm

1.  Confirm the game is active and reset is permitted.
2.  Capture a loop recap from recorded events.
3.  Restore temporary state from the blueprint's initial state.
4.  Restore the starting time and location.
5.  Clear loop-specific flags and temporary inventory.
6.  Reapply explicitly persistent unlocks and clues.
7.  Increment `currentLoop`.
8.  Record the reset event.
9.  Check the maximum loop limit.
10. Save and return the new state.

### Consistency requirement

Repeating the same action from the same state must produce the same game
mechanics outcome. Narrative wording may vary, but clue availability,
time costs, inventory, events, and ending conditions must not vary
randomly.

## 13. Gemini Integration

### Responsibilities

Gemini may: - Generate the initial scenario blueprint. - Draft character
dialogue from allowed facts. - Summarize the previous loop. - Produce
hints grounded in known clues. - Write ending narration from a validated
ending state.

Gemini must not: - Decide whether an action is permitted. - Change the
causal chain mid-game. - Invent a clue and silently add it to persistent
state. - Modify the loop counter or inventory directly. - Declare
victory without the game engine's validation. - Reveal private solution
data during normal gameplay.

### Generation workflow

1.  Validate user prompt and options.
2.  Build a constrained generation prompt.
3.  Request structured JSON from Gemini.
4.  Parse and validate using Zod.
5.  Verify all IDs and references.
6.  Validate action effect types against an allowlist.
7.  Run semantic checks for causal consistency and solvability.
8.  Retry a limited number of times if invalid.
9.  Persist only valid blueprints.
10. Return a public representation without solution fields.

### Quality rules

A playable scenario must contain: - One clearly defined central event. -
A coherent causal chain. - At least three locations. - At least three
characters, unless the scenario explicitly requires fewer. - At least
six discoverable clues. - Actions with clear time costs. - A useful
discovery in each early loop. - At least one fact that becomes useful
only after the player learns something in a previous loop. - Explicit
persistence rules for each clue and item. - Clear victory and failure
conditions. - No impossible prerequisite cycles. - A solution achievable
within the configured loop limit.

### Configuration

Use environment variables:

``` env
PORT=5000
NODE_ENV=development
MONGODB_URI=
GEMINI_API_KEY=
GEMINI_MODEL=
CLIENT_URL=http://localhost:5173
```

Choose a currently supported Gemini model and keep the model name
configurable. Never commit `.env` files or expose credentials in
client-side code or logs.

## 15. Security and Reliability

-   Keep Gemini credentials on the backend.
-   Validate all request bodies and IDs.
-   Apply rate limits to scenario generation and hint requests.
-   Configure CORS for approved frontend origins.
-   Restrict request body size.
-   Enforce session ownership on every game endpoint.
-   Never trust a client-supplied replacement game state.
-   Use allowlisted action types and effects.
-   Keep private solution data out of public responses.
-   Avoid logging secrets or session tokens.
-   Add security headers and use HTTPS in production.
-   Use timeouts and bounded retries for Gemini calls.
-   Prevent duplicate state mutations through idempotency or
    state-version checks where appropriate.
-   Handle database failures without partially advancing the game.

## 19. Definition of Done

A feature is complete only when: 1. Its UI and API behavior work
end-to-end. 2. Inputs and state transitions are validated. 3. Loading,
success, and failure states exist. 4. Security and ownership checks are
implemented where relevant. 5. Critical logic has tests. 6.
Documentation is updated.

Do not leave fake buttons, hard-coded success responses, or placeholder
logic in production paths. Mocks are acceptable for tests and explicitly
identified development fixtures.
